======================================================================
B. QUÉ EXPLICAR SOBRE TRIVY
======================================================================

MENSAJE PARA DECIR EN LA PRESENTACIÓN:

"Trivy es un scanner de seguridad para artefactos y entornos cloud-native.
En este proyecto lo utilizamos antes del despliegue para conocer qué contiene
una imagen y qué riesgos introduce. Nos permite revisar vulnerabilidades,
generar SBOM y detectar secretos. Detectar una CVE no significa automáticamente
que una imagen sea explotable; el resultado debe interpretarse considerando
severidad, versión instalada, fix disponible, exposición y contexto."

PUNTOS CLAVE:

- Detecta vulnerabilidades conocidas.
- Permite priorizar HIGH y CRITICAL.
- Identifica paquete y versión afectada.
- Muestra si existe FixedVersion.
- Puede generar JSON, HTML y SBOM.
- Puede detectar secretos.
- Trivy responde: "¿qué riesgos contiene este artefacto?"

C. DEMO TRIVY — ESCANEO EN VIVO
======================================================================

# 1) Asegurar que la imagen vulnerable esté local.
#    Si ya está local, no descarga nada.
podman image exists docker.io/library/python:3.4-alpine \

# 5) Verificar archivo
ls -lh "$EVIDENCE_DIR/trivy/python-3.4-alpine.json"

======================================================================
D. INTERPRETAR EL REPORTE TRIVY
======================================================================

# 1) Conteo por severidad
jq '
  [
    .Results[]?.Vulnerabilities[]?
  ]
  | group_by(.Severity)
  | map({
      severity: .[0].Severity,
      total: length
    })
' "$EVIDENCE_DIR/trivy/python-3.4-alpine.json"

# 2) Mostrar vulnerabilidades CRITICAL
jq -r '
  .Results[]?.Vulnerabilities[]?
  | select(.Severity == "CRITICAL")
  | [
      .VulnerabilityID,
      .PkgName,
      .InstalledVersion,
      (.FixedVersion // "SIN_FIX"),
      .Severity
    ]
  | @tsv
' "$EVIDENCE_DIR/trivy/python-3.4-alpine.json"

# 3) Mostrar HIGH/CRITICAL con fix disponible
jq -r '
  .Results[]?.Vulnerabilities[]?
  | select(
      (.Severity == "HIGH" or .Severity == "CRITICAL")
      and (.FixedVersion != null)
      and (.FixedVersion != "")
    )
  | [
      .VulnerabilityID,
      .PkgName,
      .InstalledVersion,
      .FixedVersion,
      .Severity
    ]
  | @tsv
' "$EVIDENCE_DIR/trivy/python-3.4-alpine.json" \
  | head -20

MENSAJE PARA DECIR:

"Los campos principales son:
VulnerabilityID = CVE,
PkgName = paquete afectado,
InstalledVersion = versión vulnerable,
FixedVersion = versión donde existe corrección,
Severity = prioridad inicial.

Nuestro criterio de aceptación del laboratorio es no promover una imagen con
vulnerabilidades CRITICAL con parche disponible sin una decisión de riesgo
documentada."

======================================================================
E. QUÉ EXPLICAR SOBRE COSIGN Y CHAIN OF TRUST
======================================================================

MENSAJE PARA DECIR:

"Trivy nos dice qué riesgos contiene la imagen. Cosign resuelve otra pregunta:
¿quién respalda criptográficamente este artefacto y sigue siendo exactamente
el mismo contenido que fue firmado?

La clave privada firma y debe permanecer protegida. La clave pública se utiliza
para verificar. Connaisseur recibe esa clave pública como trust root y aplica
la política dentro de Kubernetes."

DIAGRAMA:

  keys_local/cosign.key
           |
           | firma
           v
      Imagen / digest
           |
           v
      Registry HTTPS
           |
           v
  keys_local/cosign.pub
           |
           v
        verify
           |
       +---+---+
       |       |
       v       v
      OK      FAIL

Cosign responde:
  "¿esta firma corresponde a una clave en la que confío y a este digest?"

======================================================================
G. DEMO COSIGN — DEMOSTRAR QUE INICIALMENTE NO EXISTE FIRMA
======================================================================

# 1) Obtener digest de la imagen que SÍ vamos a firmar
SIGNED_DIGEST=$(skopeo inspect \
  "docker://${SIGNED_REF}" \
  | jq -r '.Digest')

SIGNED_IMAGE="${REGISTRY}/${SIGNED_REPO}@${SIGNED_DIGEST}"

echo "$SIGNED_DIGEST"
echo "$SIGNED_IMAGE"

# Guardar referencia
echo "$SIGNED_IMAGE" \
  > "$EVIDENCE_DIR/cosign-signed-image.txt"

# 2) Verificar ANTES de firmar.
#    ESTE COMANDO DEBE FALLAR.
cosign verify \
  --key keys_local/cosign.pub \
  --new-bundle-format=false \
  --insecure-ignore-tlog \
  "$SIGNED_IMAGE"

# Esperado:
# Error: no signatures found
#
# Esto es un RESULTADO POSITIVO de la prueba:
# demuestra que empezamos desde una imagen todavía no firmada.

======================================================================
H. DEMO COSIGN — FIRMA MANUAL
======================================================================

# Firmar en formato compatible con Connaisseur 3.13.0.
#
# Cosign local: 3.1.3
# Connaisseur 3.13.0 incorpora Cosign v2.x.
#
# Por compatibilidad usamos formato legacy.

cosign sign \
  --key keys_local/cosign.key \
  --new-bundle-format=false \
  --registry-referrers-mode=legacy \
  --use-signing-config=false \
  --tlog-upload=false \
  -y \
  "$SIGNED_IMAGE"

# Introducir la contraseña de keys_local/cosign.key.

# Esperado:
# Pushing signature to: 192.168.56.104:5443/<repo>

# 1) Verificar con clave correcta
cosign verify \
  --key keys_local/cosign.pub \
  --new-bundle-format=false \
  --insecure-ignore-tlog \
  "$SIGNED_IMAGE" \
  | tee "$EVIDENCE_DIR/cosign-valid.txt"

# Esperado:
# The cosign claims were validated
# The signatures were verified against the specified public key

# 2) Mostrar tag .sig creado
SIG_TAG="sha256-${SIGNED_DIGEST#sha256:}.sig"
echo "$SIG_TAG"

curl -s \
  "https://${REGISTRY}/v2/${SIGNED_REPO}/tags/list" \
  | jq .

# Debe aparecer un tag:
# sha256-....sig

======================================================================
J. DEMO KUBERNETES — IMAGEN SIN FIRMA DEBE FALLAR
======================================================================

# Antes de crear el Pod, confirmar manualmente que la imagen negativa no tiene firma:
cosign verify \
  --key keys_local/cosign.pub \
  --new-bundle-format=false \
  --insecure-ignore-tlog \
  "$UNSIGNED_REF"

# Esperado:
# Error: no signatures found

# Eliminar cualquier Pod homónimo, por seguridad.
kubectl delete pod "$UNSIGNED_POD" \
  -n supply-chain-demo \
  --ignore-not-found

# Intentar deploy.
#
# ESTE COMANDO DEBE FALLAR.
kubectl run "$UNSIGNED_POD" \
  -n supply-chain-demo \
  --image="$UNSIGNED_REF" \
  2>&1 | tee "$EVIDENCE_DIR/unsigned-deploy.txt"

# Esperado:
# admission webhook "connaisseur-svc.connaisseur.svc" denied the request
# ...
# no signatures found

# Confirmar que NO existe Pod
kubectl get pod "$UNSIGNED_POD" \
  -n supply-chain-demo

# Esperado:
# Error from server (NotFound)

MENSAJE PARA DECIR:

"Kubernetes recibió la solicitud, pero antes de crear el Pod llamó al admission
webhook. Connaisseur buscó una firma válida y no la encontró, por lo que el
objeto fue rechazado. Containerd ni siquiera necesita iniciar el workload."

======================================================================
Q. TROUBLESHOOTING RÁPIDO
======================================================================

1) kubectl intenta localhost:8080
--------------------------------
export KUBECONFIG=/etc/kubernetes/admin.conf
kubectl get nodes

2) Registry no responde
------------------------
curl -v "https://${REGISTRY}/v2/"

3) Connaisseur no está Running
------------------------------
kubectl get pods -n connaisseur -o wide

kubectl logs \
  -n connaisseur \
  -l app.kubernetes.io/name=connaisseur \
  --tail=200

4) Error x509 unknown authority dentro de Connaisseur
-----------------------------------------------------
kubectl get deployment connaisseur \
  -n connaisseur \
  -o jsonpath='{range .spec.template.spec.containers[?(@.name=="connaisseur")].env[*]}{.name}={.value}{"\n"}{end}'

Debe existir:

SSL_CERT_FILE=/etc/connaisseur-registry-ca/ca-bundle.crt

Comprobar ConfigMap:

kubectl get configmap connaisseur-registry-ca \
  -n connaisseur

5) Cosign manual funciona pero Connaisseur dice "no signatures found"
----------------------------------------------------------------------
La firma debe crearse en formato compatible:

cosign sign \
  --key keys_local/cosign.key \
  --new-bundle-format=false \
  --registry-referrers-mode=legacy \
  --use-signing-config=false \
  --tlog-upload=false \
  -y \
  "$SIGNED_IMAGE"

6) Imagen sin firma es aceptada inesperadamente
-----------------------------------------------
Verificar que el namespace tenga:

kubectl get namespace supply-chain-demo --show-labels

Debe incluir:

securesystemsengineering.connaisseur/webhook=validate

Revisar policy efectiva:

helm get values connaisseur -n connaisseur

7) El repository de demo ya tiene firma
---------------------------------------
NO reutilizar el repository.
Generar un nuevo DEMO_ID:

DEMO_ID="$(date +%Y%m%d%H%M%S)"

y repetir con repositories nuevos.
